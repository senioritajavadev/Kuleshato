# Kuleshato

Kuleshato — локальный консольный помощник, **строго предназначенный для Java-проектов**. Реализация CLI написана на Java 21 и работает с локальной моделью Ollama. Приложение не требует API-ключа и не отправляет запросы к облачным AI-сервисам.

Что умеет:

- **Ответы о проекте с доказательствами.** Факты о сборке, CI, командах и настройках извлекаются детерминированно с указанием `файл:строка` и вида источника; утверждения модели показываются, только если подтверждены переданными строками кода, тестов или документации.
- **Безопасное изменение кода.** Каждая правка — через diff и подтверждение; обнаруженные команды проверки запускаются сами, остальные — с подтверждением; итог (изменённые файлы, отказы, результаты проверок) печатает приложение, а не модель.
- **Ревью Java-кода** (`/review`): файл, метод или текущий diff; замечания с приоритетом, `файл:строки`, риском, основанием и способом воспроизведения; вкусовые замечания не выдаются за дефекты.
- **Память и уроки:** заметки проекта и уроки на будущее в `.kuleshato/memory.md`, запись уроков — только с подтверждением.
- **Эталонный набор** с порогами качества в `test.ps1` и CI и живым замером модели на вашем оборудовании.

## Требования

- JDK 21 или новее;
- [Ollama](https://ollama.com/) с загруженной моделью `qwen3:8b`.

```powershell
ollama pull qwen3:8b
ollama serve
```

Соберите исполняемый JAR из каталога проекта:

```powershell
.\build.ps1
```

Если установлен Maven, скрипт собирает проект через `mvn package`; иначе использует `javac` из JDK.
Для установки команды `Kuleshato` в пользовательский `PATH` из каталога проекта выполните:

```powershell
.\install.ps1
```

Это создаёт пользовательский launcher без прав администратора и ставит его выше возможного устаревшего npm-launcher. После установки команду можно запускать из любого Java-проекта; для уже открытых терминалов путь обновляется сразу.

Запускайте помощника из Java-проекта:

```powershell
..\kuleshato\kuleshato.bat
```

Или напрямую:

```powershell
java -Dstdout.encoding=UTF-8 -Dstderr.encoding=UTF-8 -Dfile.encoding=UTF-8 -jar ..\kuleshato\target\kuleshato.jar "Объясни структуру Java-проекта"
```

Параметры `--model`, `--ollama-url`, `--cwd` и `--resume <ID>` позволяют выбрать модель, loopback-адрес Ollama, рабочий каталог и сессию. Переменные `KULESHATO_MODEL` и `KULESHATO_OLLAMA_URL` также поддерживаются. Ollama разрешён только по loopback HTTP-адресу.

При запуске проверяется рабочий каталог: Java-исходники должны находиться в корне, в дереве `src` или сопровождаться конфигурацией Maven/Gradle. Случайный `.java`-пример в документации без признаков Java-проекта не считается достаточным. Если Java-проект не обнаружен, Kuleshato завершает работу с объяснением; он не переключается в универсальный режим. Папки сборки, IDE и зависимости исключены из проверки. `/brief` формирует обзор Java-версии, Maven/Gradle, тестов, CI и документации, читая имена файлов и ограниченный объём манифестов без запуска команд. Каждый факт обзора сопровождается происхождением: `файл:строка — вид источника` (конфигурация, документация или структура файлов) и, если факт выведен, основанием — например, «стандартная фаза Maven» или «по имени скрипта». Извлекаются координаты и модули Maven/Gradle, версия Java (с предупреждением о расхождениях), wrapper, главный класс, зависимости, плагины и тестовые фреймворки; шаги, триггеры и версия Java в GitHub Actions, GitLab CI, Jenkins, CircleCI и Azure Pipelines; команды из блоков кода README; `gradle.properties`, `.mvn/*.config`, `.sdkmanrc`/`.java-version` и ключи `application*.properties|yml`. Значения, которые могут быть секретами, не показываются; DOCTYPE в `pom.xml` запрещён. Выведенные команды не запускаются и обозначены как непроверенные.

Для вопросов о том, как устроен проект, и просьб его изучить Kuleshato сам прикладывает структурный обзор, выполняет ограниченный поиск по исходникам и конфигурации и читает релевантные файлы с номерами строк. В пределах бюджета контекста в первую очередь включаются `Main.java`, файл обращения к Ollama (`OllamaBackend.java` в Kuleshato или `OllamaClient.java` в типичном проекте) и Maven/Gradle-конфигурация; каждый файл получает собственный лимит, чтобы один большой исходник не вытеснил остальные. Для больших файлов выбираются фрагменты вокруг совпадений и ключевых участков (например, вызовов `/api/chat`); исходные номера строк сохраняются, а пропущенные строки нельзя процитировать. Каждая переданная строка получает стабильный ID (`E00001` и т. д.): модель ссылается на ID, а приложение само разрешает его в проверенный путь и номер строки. Общие слова запроса отбрасываются; лимит отображаемых совпадений не прерывает сам поиск. В терминале показываются прочитанные файлы и найденные совпадения. Латинские идентификаторы и названия технологий в тезисе (например, `OrderRepository`, `Kafka`, `Calc.add`) должны встречаться в процитированных строках или пути процитированного файла, иначе тезис отклоняется. Исходники модулей (`<модуль>/src/main/java`) и простых раскладок (`src/*.java`) считаются исполняемым кодом; если после первого прохода остаётся бюджет контекста, он отдаётся усечённым файлам. Приложение показывает только тезисы, подтверждаемые привязанными к ним строками, и отдельно выдаёт автоматический структурный обзор, не выдавая его за анализ поведения программы. Документальные выводы показываются отдельно от подтверждённых по коду и явно обозначаются как заявления документации. Если ссылки отклонены или ответ имеет неверный JSON-формат, приложение делает одну повторную попытку с соответствующей инструкцией. Если формат не исправлен, Kuleshato сообщает о проблеме и выдаёт только детерминированные результаты сканирования, не подставляя неподтверждённые тезисы. Поиск ограничен размером и типами файлов: отсутствие совпадений не доказывает отсутствие функции, а совпадение само по себе не доказывает её наличие.

В ответах о проекте дополнительно отображаются фактические параметры текущего запуска — выбранная модель и адрес Ollama из аргументов командной строки, переменных окружения или настроек проекта. Доступность сервера и наличие модели отдельно не проверяются и так и обозначаются.

По умолчанию используется Ollama на `http://127.0.0.1:11434`, контекст до 40 960 токенов и включённый Thinking. Автосжатие начинается примерно при заполнении 65% контекстного окна и сокращает историю примерно до 30%, с ограничениями 26 000 и 12 000 токенов. Все запросы (диалог, ответы о проекте, ревью, планы) используют одно окно `contextWindow`: при смене окна Ollama перезагружает модель.

Для видеокарты с 8 ГБ (например, RTX 4060) и `qwen3:8b` окно 40 960 не помещается: кэш контекста занимает около 5,8 ГБ, и почти половина слоёв уходит на процессор. Замер на RTX 4060 8 ГБ под Windows: окно 12 288 — 13% модели на CPU, окно 8 192 — `100% GPU` (6,2 ГБ). Рекомендуется `"contextWindow": 8192` в `.kuleshato/config.json`; проверить можно командой `ollama ps` — в колонке PROCESSOR должно быть `100% GPU`. С меньшим окном автосжатие истории срабатывает раньше.

Для ответов о проекте используется отдельный облегчённый запрос: инспекция ограничена 6 000 символами; Thinking отключён, а длина ответа ограничена 192 токенами. Таймаут такого запроса составляет 2 минуты; если модель не успевает, Kuleshato выводит детерминированный обзор проекта и причину. Проверка описания самого Kuleshato обрабатывается локально по результатам инспекции и не ждёт модель.

На просьбу рассказать о проекте в целом («Изучи проект и расскажи мне о нём», «Что это за приложение?», «Tell me about this project») Kuleshato отвечает сразу и без модели: описание и заявленные возможности из README (с номерами строк), структурный обзор сборки и тестов, а также карту кода по всем исходникам — точку входа, технологии со ссылкой на первую строку использования (JDBC, Spring, JPA, консольный ввод, Kafka и др.), пакеты, классы и их методы. Карта строится по объявлениям в коде и не описывает поведение методов; о конкретной части проекта можно спросить отдельно. Если README нет, обзор составляется только по коду и манифестам.

Вопросы о назначении проекта, например «для чего он создан», отвечаются по вводному описанию `README.md` без ожидания генерации модели. Kuleshato указывает строку документации и отмечает, что это описание автора проекта, а не независимая проверка всех возможностей.

Короткие продолжения вроде «что в нём можно улучшить?», «а какие там тесты?» или «а модули?» связываются с недавним явным вопросом о проекте в текущей сессии (в том числе через цепочку таких продолжений). Вопрос, где упомянут класс, существующий в проекте (например, `PriceCalculator`), тоже обрабатывается в режиме инспекции. Тезисы, подтверждённые только тестовыми файлами, показываются отдельной группой «Подтверждено по тестам». Обзор также определяет фреймворк приложения (Spring Boot, Quarkus, Micronaut) и разрешает зависимости и плагины из каталога версий Gradle. Для таких запросов Kuleshato быстро формирует ограниченный список улучшений по обнаруженной структуре, не выдавая его за полноценное ревью кода и не ожидая долгую генерацию модели.

Формулировки «о чём код?» и «изучи проект, расскажи о нём» дают быстрый обзор по вводному описанию README и структурному сканированию. Ответ явно различает документацию и то, что реально проверено по коду.

## Интерактивные команды

| Команда | Что делает | Пример простыми словами |
|---|---|---|
| `/help` | Показать команды и примеры. | Введите `/help`, если забыли, как начать новую сессию. |
| `/clear` | Очистить историю сообщений текущей сессии. | Введите `/clear`, чтобы начать разговор заново, не меняя файлы проекта. |
| `/compact` | Сжать историю диалога. | Введите `/compact`, если разговор стал длинным, но его контекст нужно сохранить. |
| `/memory` | Показать память проекта из `.kuleshato/memory.md`. | Введите `/memory`, чтобы посмотреть сохранённые правила проекта. |
| `/memory init` | Создать шаблон памяти; требуется подтверждение. | Введите `/memory init`, чтобы начать записывать, например, версию Java и команды тестирования. |
| `/memory reload` | Перечитать память и обновить контекст. | После редактирования `memory.md` введите `/memory reload`. |
| `/settings` | Показать активные настройки. | Введите `/settings`, чтобы узнать, какая модель выбрана. |
| `/settings init` | Создать `.kuleshato/config.json`; требуется подтверждение. | Введите `/settings init`, чтобы настроить модель для проекта. |
| `/settings reload` | Перечитать настройки без перезапуска. | После изменения `config.json` введите `/settings reload`. |
| `/skills` | Показать навыки, описание и примеры использования. | Введите `/skills`, чтобы найти навык для проверки кода или сохранения правил. |
| `/skill enable <имя>` | Включить навык в текущей сессии. | Например, `/skill enable remember`, затем попросите: «Предложи, что из нашего обсуждения сохранить в память». |
| `/skill disable <имя>` | Выключить навык в текущей сессии. | Введите `/skill disable java-notes`, если не хотите использовать персональные Java-предпочтения в этой сессии. |
| `/brief [путь]` | Составить краткий обзор Java-проекта или подкаталога. | Введите `/brief src`, чтобы получить обзор исходников. |
| `/review <цель>` | Ревью файла, каталога, метода (`Класс#метод`) или текущего `diff` относительно HEAD. | `/review OrderService#placeOrder` или `/review diff` перед коммитом. |
| `/plan <цель>` | Составить и сохранить план с помощью локальной модели. | Например, `/plan Добавить валидацию REST-запросов`. |
| `/plan` | Показать текущий план. | Введите `/plan`, чтобы посмотреть следующие шаги. |
| `/plan done [номер]` | Отметить шаг плана; без номера отмечается следующий незавершённый. | Введите `/plan done 2`, когда закончите второй шаг. |
| `/plan clear` | Удалить план. | Введите `/plan clear`, если задача больше не актуальна. |
| `/new` | Начать новую сессию. | Введите `/new`, чтобы перейти к другой задаче в этом же проекте. |
| `/sessions` | Показать сохранённые сессии текущего проекта. | Введите `/sessions`, чтобы найти прошлый разговор. |
| `/resume <ID>` | Возобновить сессию с её планом и навыками. | Скопируйте ID из `/sessions` и выполните `/resume <ID>`. |
| `/exit` | Завершить работу. | Введите `/exit`, когда закончите. |

### Навыки

Навык добавляет к разговору инструкции для повторяемого типа работы. `/skills` показывает описание, простую фразу-пример и команду включения. После включения можно просто попросить Kuleshato выполнить задачу своими словами.

| Навык | Что делает | Пример просьбы |
|---|---|---|
| `java-notes` | Учитывает Java-предпочтения и заметки по Java, тестированию, SQL/JDBC, Spring и Kafka. Включён в новой сессии по умолчанию. | «Проверь этот класс по моим Java-предпочтениям и объясни улучшения». |
| `verify` | Помогает подобрать и проверить команды сборки и тестирования Java-проекта. | «Проверь, как собрать и протестировать этот Java-проект». |
| `simplify` | Ищет ненужную сложность и предлагает безопасно упростить код. | «Упрости этот метод, сохранив его поведение». |
| `skillify` | Помогает подготовить новый переиспользуемый навык Kuleshato. | «Создай навык для проверки Java-кода перед code review». |
| `remember` | Предлагает устойчивые правила и решения для памяти проекта; сам не записывает их без подтверждения. | «Предложи, какие постоянные правила проекта стоит сохранить в памяти». |

Например, для сохранения новых соглашений: `/skill enable remember`, затем «Мы используем Java 21 и Maven. Предложи, что добавить в память проекта». Для создания повторяемого процесса: `/skill enable skillify`, затем «Подготовь навык, который проверяет REST-контроллер и тесты перед ревью». Новый навык сохраняется только после явного одобрения и подтверждения изменения файла.

В новой сессии по умолчанию включён `java-notes`; его можно выключить через `/skill disable java-notes`, а `/new` включает его снова. Навыки добавляют инструкции к контексту, но не запускают скрипты автоматически. Проверки Maven/Gradle и другие shell-команды требуют отдельного подтверждения при каждом запуске. Создание или изменение файлов показывает diff и также требует подтверждения. Без интерактивного терминала операции, требующие подтверждения, отклоняются.

История хранится локально в `%USERPROFILE%\.kuleshato\sessions` и может быть возобновлена только для исходного рабочего каталога. Память и настройки хранятся в `.kuleshato/` внутри Java-проекта. Не сохраняйте в них секреты.

## Память и уроки

`.kuleshato/memory.md` подмешивается в системную подсказку каждого запроса как пользовательские заметки (не системные инструкции). Память может занимать не больше 15% окна контекста (оценка — 3 символа на токен; для окна 8 192 это около 3 700 символов). Если файл больше, модели передаётся его начало с явной пометкой о сокращении, а Kuleshato предупреждает при запуске, в `/memory` и `/memory reload` — ничего не обрезается молча.

Уроки на будущее собираются в раздел `## Уроки` той же памяти:

- модель может завершить ответ строкой `[[LESSON краткое правило]]`; маркер вырезается из ответа;
- урок предлагается к записи, только если в запросе зафиксирована ошибка: проверка упала или исчерпан лимит исправлений, изменение отклонено, или вы сами указали на ошибку («ты ошибся», «неправильно»…). Без такого признака урок отбрасывается с сообщением;
- запись — всегда через diff и подтверждение `[y/N]`; повторы, уроки длиннее 200 символов и похожие на секреты не записываются;
- если проверка так и не прошла, Kuleshato предлагает сформулировать урок самостоятельно (Enter — пропустить): урок от человека надёжнее самооценки модели;
- урок можно в любой момент дописать вручную и применить через `/memory reload`.

Так текст модели или файлов проекта не становится постоянной инструкцией без вашего подтверждения. Пользу уроков для модели измеряет эталонный набор: задача с уроком (`lesson` в `tasks`) в живом прогоне решается дважды — с уроком и без, а `-Compare` показывает результат отдельной колонкой.

## Настройки проекта

После `/settings init` можно редактировать файл:

```json
{
  "model": "qwen3:8b",
  "ollamaUrl": "http://127.0.0.1:11434",
  "contextWindow": 40960,
  "autoCompact": true,
  "autoRunChecks": true,
  "backend": "ollama"
}
```

`contextWindow` должен быть от 4096 до 131072. Адрес Ollama должен быть loopback HTTP. Аргументы запуска и переменные окружения переопределяют файл настроек. `autoRunChecks: false` возвращает подтверждение каждой команды, включая проверки. `backend` выбирает адаптер модели; сейчас поддерживается только `ollama`, неизвестное значение отклоняется. Протокол модели (`ModelBackend`) отделён от цикла инструментов (`ModelClient`) и проверки фактов, так что новый адаптер подключается без изменения проверок.

## Изменение кода

Для просьб изменить код Kuleshato следует сценарию: изучить нужные файлы → короткий план → изменения через `edit_file`/`write_file` → подходящая проверка → итог.

- Каждое изменение файла показывается как diff и применяется только после подтверждения. Отклонённое изменение не повторяется.
- Команды проверки, обнаруженные в конфигурации проекта (стандартные цели Maven/Gradle вроде `mvn test`, `.\gradlew.bat build` и корневые скрипты `test.*`/`build.*`), запускаются без отдельного подтверждения, если модель вызывает их дословно; Kuleshato сообщает о каждом таком запуске и его основании. Команды из CI и README, команды с `;`, `|`, `&`, `>`, `$` и любые другие команды требуют подтверждения. Учтите, что тесты и скрипты сборки исполняют код проекта.
- Модель получает сокращённый вывод команды: начало, строки с ошибками и конец (около 6000 символов).
- `read_file` отдаёт файл фрагментами: по умолчанию до 200 строк (не больше 400 и 12 000 символов) начиная с `start_line`; если файл длиннее, первая строка ответа в квадратных скобках указывает диапазон и следующий `start_line`. Сами строки не меняются, поэтому их можно дословно использовать в `edit_file`. Это защищает небольшое окно контекста (например, 8192) от переполнения одним большим файлом. Идея взята из [benjamin-plus](https://github.com/JetBrains/benjamin-plus-skill/), но встроена в инструмент, а не в подсказку, чтобы не зависеть от послушания небольшой модели. Просьбу о «разведке за один проход» (несколько инструментов в одном ответе) пробовали и убрали: в парном живом замере на `qwen3:8b` с ней задачи решались хуже.
- Ошибки инструментов подсказывают небольшой модели, как исправиться (выявлено по трассам живого замера на `qwen3:8b`):
  - несуществующий путь (например, угаданный `src/test/java`) — ответ перечисляет содержимое ближайшего существующего каталога и советует искать по всему проекту;
  - `search_files` принимает каталог или один файл и находит совпадения и в содержимом, и в именах файлов;
  - искажённая запись обнаруженной проверки (`./test.cmd`, `test.cmd`, табуляция вместо `\t` после потери обратной косой черты в JSON) запускается как сама проверка с пояснением для модели; подставляется только команда из списка обнаруженных, остальные по-прежнему требуют подтверждения;
  - если `old_text` в `edit_file` не найден дословно, допускается совпадение без учёта переводов строк (`\n`/`\r\n`) и отступов — только единственное, и изменение всё равно показывается как diff; иначе ответ называет первую строку `old_text`, которой нет в файле, показывает самые похожие строки файла с номерами и какой фрагмент перечитать;
  - если в `edit_file` нет `new_text`, ответ объясняет, что он обязателен, а для удаления передаётся пустая строка.
- Если пользователь просил изменение, а модель закончила ход описанием или планом без единой правки, приложение один раз напоминает ей внести исправление и запустить проверку (или объяснить, почему изменение не нужно). Напоминания нет, если файлы уже изменены, изменение или команда отклонены пользователем, проверка в этом ходе прошла или исчерпан лимит проверок; о напоминании печатается строка `◇ Kuleshato: …`.
- За один запрос допускается не больше 3 неудачных проверок; после этого проверка не запускается, а модель должна сообщить об ошибке.
- После ответа приложение само печатает итог: изменённые и отклонённые файлы, отклонённые команды, запущенные команды с кодом завершения, предупреждение, если после изменений проверка не запускалась или упала. Этот итог формируется не моделью, поэтому отказ или ошибка не маскируются под успех.

## Ревью кода

`/review` принимает файл или каталог, метод `Класс#метод` (все перегрузки вместе с javadoc и аннотациями) или `diff` — изменения Java-файлов относительно HEAD, включая новые неотслеживаемые файлы и удалённые строки. Строки для ревью выбирает приложение (до 16 000 символов) и нумерует их ID; модель возвращает замечания со ссылками на эти ID, а приложение проверяет каждое:

- ссылки должны указывать на переданные строки; идентификаторы в обратных кавычках должны встречаться в процитированном коде;
- нужны приоритет P1–P3, категория (дефект, регрессия, дублирование, сложность), риск, основание и условие воспроизведения;
- замечания о стиле и именовании, выданные за дефект, отклоняются; дублирование и сложность не поднимаются выше P3;
- «регрессия» должна касаться изменённых строк или строк рядом с удалёнными, иначе считается дефектом.

Вывод начинается с дефектов и регрессий, затем идут дублирование и сложность; для каждого замечания указаны `файл:строки`, процитированный код и способ воспроизведения. Отклонённые замечания перечисляются отдельно. Ревью всегда заканчивается оговоркой, что отсутствие замечаний не доказывает отсутствие ошибок.

## Разработка

Устройство кода (`src/main/java/kuleshato`):

| Класс | Назначение |
|---|---|
| `Main`, `TerminalUI` | CLI, команды, системная подсказка, итог выполнения и уроки |
| `ModelBackend`, `OllamaBackend` | протокол модели (транспорт); выбор адаптера — настройка `backend` |
| `ModelClient` | цикл вызова инструментов, сжатие истории, структурированные ответы, ревью и планы |
| `WorkspaceTools`, `CommandPolicy` | файловые инструменты, подтверждения, автозапуск проверок, лимит циклов, итог хода |
| `ChangeNudge` | однократное напоминание модели, которая описала исправление, но не внесла его |
| `JavaProjectBrief`, `ProjectFacts` | обзор проекта и детерминированные факты с происхождением |
| `ProjectOverview` | ответ «расскажи о проекте»: возможности из README и карта кода (пакеты, классы, методы, технологии) |
| `ProjectInspection`, `ProjectAnswering` | сбор доказательств, маршрутизация и проверка ответов о проекте |
| `CodeReview` | выбор строк для ревью и проверка замечаний |
| `ProjectMemory`, `Lessons` | память проекта, бюджет контекста, уроки |
| `ProjectConfig`, `SessionStore`, `SkillRegistry` | настройки, сессии, навыки |
| `JavaProject`, `Json` | проверка, что каталог — Java-проект; минимальный JSON без зависимостей |

Тесты — `src/test/java/kuleshato/TestSuite.java`; эталонный набор — `ProjectBenchmark` и `src/test/resources/benchmark`.

Для сборки и запуска проверок достаточно JDK:

```powershell
.\build.ps1
.\test.ps1
```

При установленном Maven `.\test.ps1` запускает тесты через Surefire/JUnit; без Maven используется встроенный тестовый раннер на JDK, не требующий загрузки зависимостей. Целевая версия компиляции — Java 21.

### Эталонный набор

`src/test/resources/benchmark/cases.json` описывает учебные проекты (`fixtures/*.project`: Maven-сервис, многомодульный Gradle CLI, Java без системы сборки, многомодульный Spring Boot на Maven с крупным файлом, Kotlin DSL с каталогом версий `libs.versions.toml`), ожидаемые факты с файлом, строкой и видом источника, а также вопросы с ожидаемым маршрутом ответа, обязательным и запрещённым содержанием. Для вопросов, требующих модели, заданы тезисы с пометкой «код», «тесты», «документация» или «отклонить» (выдуманная технология, неверное число, отрицательное утверждение, несуществующий ID).

```powershell
.\benchmark.ps1                      # детерминированный прогон: метрики и пороги
.\benchmark.ps1 -Live -Model qwen3:8b # дополнительно — вопросы, задачи и ревью на локальной модели Ollama
.\benchmark.ps1 -Live -ContextWindow 8192 -Record -Hardware "RTX 4060 8GB, 16GB RAM"  # дописать результат в benchmark-results\live.jsonl
.\benchmark.ps1 -Live -LiveOnly tasks -ContextWindow 8192 -Record  # живой прогон только задач (questions/tasks/reviews)
.\benchmark.ps1 -Live -LiveOnly tasks -ContextWindow 8192 -Reading legacy -Record  # то же с чтением файлов целиком — для парного сравнения
.\benchmark.ps1 -Compare               # таблица сравнения моделей по всем записанным прогонам
```

Раздел `tasks` содержит задачи на изменение кода (Java-проект с падающей проверкой `javac` + `java`): эталонное решение прогоняется через настоящий цикл агента со сценарной моделью, а результат определяется независимым запуском проверки и сравнением файлов — модельному «готово» не доверяют. Раздел `reviews` содержит код с известными дефектами (ресурсы и границы, безопасность — SQL-инъекция и обход пути, конкурентность, `@Transactional` в Spring), корректный код, «ловушки» вкусовых замечаний (именование, внедрение через поле) и git-diff с регрессией; проверяется выбор строк для ревью и обработка заранее заданных замечаний (приняты, понижены или отклонены). В живом прогоне задачи решает настоящая модель (правки одобряются автоматически, прочие команды отклоняются), а ревью считает найденные известные дефекты и прочие замечания.

Измеряются полнота и точность фактов, точность ссылок, отсутствие утечки секретов, доставка нужных строк в контекст модели, приём подтверждённых и отклонение неподтверждённых тезисов, различение кода и документации и проверки ответов. Детерминированный прогон входит в `.\test.ps1` и CI (`.github/workflows/ci.yml`) и падает при нарушении порогов. Живой прогон печатает время, число вызовов модели, принятые/отклонённые тезисы и покрытие ключевых фактов; он зависит от модели и оборудования и в CI не запускается. С `-Record` результат вместе с моделью, ОС, числом ядер и детерминированными метриками дописывается в `benchmark-results/live.jsonl`, чтобы сравнивать модели во времени. Оборудование JVM не определяет само — укажите его через `-Hardware` или `KULESHATO_HARDWARE`. `-Compare` строит по этому файлу таблицу для каждой пары «модель + адаптер + оборудование»: время ответа, доля ответов без резервного вывода (валидность JSON и ссылок), принятые тезисы и нарушения, решённые задачи, упавшие проверки и ошибки инструментов, найденные известные дефекты в ревью и скорость генерации (токенов в секунду по данным Ollama). Для каждой задачи живой прогон печатает и записывает краткую трассу: вызовы инструментов с главными аргументами, их исход (✓/✗ с текстом ошибки) и ответ модели, — по ней видно, почему задача не решена. Записи с разной версией подсказки сценария (`workflow`) и разным режимом чтения (`-Reading keyhole|legacy`) попадают в разные строки таблицы.
