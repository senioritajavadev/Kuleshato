# Java-практики и учебные заметки

Используй этот навык как предпочтения и справочный конспект пользователя, а не как неизменные требования к каждому проекту. Сначала изучай текущие исходники, сборку, версии и соглашения проекта. Не переписывай работающий проект под эти заметки без необходимости. Если заметка расходится с фактическим API, версией библиотеки или контекстом, объясни расхождение и предложи актуальный вариант.

Если пользователь учится, объясняй по шагам: сначала понятие, затем небольшой пример, затем как проверить понимание. Для задач предлагай тесты и разбирай, почему решение работает; не перегружай ответ ненужной теорией.

## Java и организация кода

- При обучении связывай базовые понятия с кодом: метод объявляет параметры, вызов передаёт аргументы; `for` удобен при известном числе повторений, enhanced `for` — для обхода элементов, `while` — пока условие истинно, `do-while` — когда тело должно выполниться хотя бы раз.
- Объясняй ООП на конкретной задаче: инкапсуляция защищает состояние, интерфейсы задают контракт, наследование выражает отношение «является», полиморфизм позволяет работать через общий тип. Предпочитай композицию, если она проще и не создаёт искусственную иерархию.
- Используй generics и коллекции для явных типов данных; не возвращай изменяемое внутреннее состояние без необходимости. Различай интерфейс коллекции и её конкретную реализацию.
- Предпочитай понятные имена, явные импорты без wildcard, небольшие методы и классы с одной связной ответственностью.
- Разделяй web/API, бизнес-логику и доступ к данным, когда такая архитектура подходит масштабу проекта. Не создавай пакеты или абстракции только ради формального шаблона.
- Репозитории/DAO должны скрывать детали хранения за ясным API; используй интерфейс и отдельную реализацию, если это улучшает заменяемость или тестирование, а не автоматически в любом проекте.
- Используй `record` для небольших неизменяемых DTO/value-типов, если это соответствует контракту. Не превращай JPA-сущности в records. Закрытые наборы значений моделируй через `enum`; не сохраняй `ordinal()` как постоянный идентификатор.
- Старайся явно задавать контракты вместо случайного `null`: проверяй обязательные входы, используй подходящий тип результата и `Optional` там, где он улучшает API. Не оборачивай каждое поле или параметр в `Optional` и не маскируй отсутствие данных значениями по умолчанию.
- Для денежных значений используй `BigDecimal` с явным масштабом и режимом округления. `double` подходит для приближённых вычислений, но не для точных сумм.
- Сохраняй простую архитектуру: абстракции должны решать конкретную проблему. Проверяй бизнес-логику, границы ответственности, инкапсуляцию и неизменяемость возвращаемых коллекций (`List.copyOf`, если нужна неизменяемая копия).
- Используй Lombok только если он уже принят проектом и присутствует в сборке. `@Slf4j` допустим при такой конвенции; иначе используй принятый проектом логгер.
- В прикладном коде не используй `System.out.println`/`printStackTrace` для ошибок. Обрабатывай ожидаемые ошибки подходящим уровнем, сохраняя причину; логируй значимые события без секретов, персональных данных и избыточного шума.
- Закрывай ресурсы через try-with-resources. Не подавляй исключения пустыми `catch` и не подменяй ошибки сообщением об успехе.

## Сборка и тестирование

- Сохраняй версии Java, Spring и зависимостей, уже принятые проектом. Не обновляй всё до «самого нового» автоматически: учитывай совместимость, BOM/parent проекта, changelog и минимальные изменения.
- Пиши unit-тесты для поведения и граничных случаев с JUnit. Mockito полезен для изоляции внешних зависимостей; не мокируй простые значения и саму тестируемую логику.
- Проверяй не только happy path, но и ошибки, пустые значения, дубликаты и повторные операции. Для слоя Spring добавляй целевые MVC/JPA/integration-тесты по необходимости.
- Для многопоточности и конкурентного доступа явно проверяй гонки и целостность данных; не предполагай, что синхронный вызов или тест с одним потоком доказывает корректность.

## SQL, JDBC и хранение данных

- Используй `PreparedStatement` и связанные параметры для всех значений из ввода; не склеивай пользовательский ввод с SQL. Имена таблиц/столбцов обычно нельзя безопасно передать как bind-параметры — для динамических идентификаторов применяй строгий allowlist.
- В JDBC предпочитай управляемый `DataSource` с пулом соединений в многопоточном/серверном приложении. Используй `DriverManager` только для простых локальных сценариев, если так устроен проект.
- Закрывай `Connection`, `PreparedStatement` и `ResultSet` через try-with-resources. Выбирай `executeQuery`, `executeUpdate` или `execute` по ожидаемому результату.
- Храни длинные SQL-запросы читабельными; Java text blocks удобны, если целевая версия проекта их поддерживает. Учитывай SQL-диалект фактической базы.
- В запросах используй устойчивую сортировку для пагинации. `LIMIT/OFFSET` прост, но на больших или часто меняющихся наборах может быть дорогим/нестабильным; рассмотри keyset-пагинацию, если это оправдано.
- Для группировки помни различие `WHERE` (фильтр строк до группировки) и `HAVING` (фильтр групп). Выбирай `JOIN` по требуемой семантике и проверяй возможные дубликаты строк.
- Выбирай только нужные столбцы, если нет причины загружать всю строку. Учитывай SQL `NULL` трёхзначную логику (`IS NULL`/`IS NOT NULL`), проверяй скобки в сочетании `AND`/`OR` и используй `IN` для списков значений.
- Подбирай SQL-типы по смыслу: `NUMERIC/DECIMAL` для точных сумм, целые типы для счётчиков, `DATE` для календарной даты и подходящий `TIMESTAMP` для времени. В PostgreSQL целочисленное деление отбрасывает дробную часть; используй точный дробный тип, когда требуется дробный результат. Для интервалов дат и времени учитывай тип, часовой пояс и диалект.
- Транзакция должна охватывать согласованную единицу бизнес-работы. Выбирай уровень изоляции по требуемым гарантиям и стоимости; обрабатывай конфликты, deadlock и retry только с подходящей стратегией.
- Используй версионирование/optimistic locking для защиты обновлений от потери конкурентных изменений, когда это соответствует модели. Обычно обновление проверяет одновременно идентификатор и текущую версию, увеличивает версию и считает изменённые строки; ноль строк означает конфликт или отсутствие актуальной записи.
- Soft delete применяй только при требованиях аудита/восстановления: помечай запись временем/признаком удаления, исключай её во всех чтениях и обновлениях, проверяй связи и ограничения. Удаление должно быть явно отражено в API и бизнес-правилах.
- Управляй изменениями схемы версионируемыми миграциями (например, Flyway или Liquibase, если они уже используются). Не очищай схему/базу и не применяй разрушительные DDL-команды без явного подтверждения и проверенного бэкапа.
- Пагинацию, batch и fetch size вводи после понимания драйвера и объёма данных; проверь реальное поведение и производительность.

## Spring и REST

- Используй constructor injection для обязательных зависимостей. Настраивай бины через существующий стиль проекта; профили и `@Qualifier`/`@Primary` применяй при реальной необходимости.
- Разделяй HTTP-обработку, бизнес-логику и хранение данных. Для REST-контроллеров валидируй входные DTO и возвращай подходящие HTTP-статусы; ошибки обрабатывай согласованно, например, через `@ControllerAdvice`.
- Не отдавай JPA-сущности напрямую во внешний API: DTO помогают контролировать контракт, скрывать внутренние/чувствительные поля и управлять ленивой загрузкой. Загружай нужные связи запросом, проекцией или `EntityGraph`; `@Transactional` держи вокруг подходящей сервисной операции. Не включай Open Session in View просто для сокрытия ошибки.
- Spring AOP, `@Transactional` и другие прокси-интерцепторы срабатывают через вызов прокси; учитывай ограничения self-invocation и видимость методов.
- Для конфигурации безопасности различай аутентификацию (кто пользователь) и авторизацию (что разрешено). Применяй принцип наименьших привилегий, проверяй доступ на сервере и отдельно тестируй 401 и 403.
- Не отключай CSRF автоматически: решение зависит от способа аутентификации, браузерных cookie и модели угроз. Stateless API не означает автоматически, что любая конфигурация безопасна.
- Для паролей используй штатный `PasswordEncoder` с адаптивным хешированием. Для OAuth2/JWT предпочитай поддерживаемые механизмы Spring Security Resource Server вместо самописного разбора/проверки токенов. Никогда не храни секреты в исходниках.
- Используй API и конфигурацию, поддерживаемые версией Spring проекта; не копируй устаревшие примеры вроде `WebSecurityConfigurerAdapter`.

## Kafka и асинхронная обработка

- Учитывай, что порядок гарантируется внутри партиции, а consumer group делит партиции между участниками. Выбирай ключ сообщения исходя из требуемого порядка и распределения нагрузки.
- Обработка сообщений должна учитывать повторную доставку: проектируй идемпотентные операции, явную стратегию повторов с ограничениями и dead-letter topic для сообщений, которые не удалось обработать.
- Асинхронная отправка требует обработки результата/ошибки; синхронный `get()` блокирует поток и сам по себе не даёт бизнес-гарантии «ровно один раз».
- Используй Kafka-транзакции и гарантии exactly-once только если конфигурация, границы Kafka/БД и требования приложения действительно их обеспечивают; поясняй ограничения.

## Локальная среда

- Для Maven/Spring Boot предпочитай Maven Wrapper (`mvnw`/`mvnw.cmd`), если он включён в проект, чтобы использовать закреплённую версию Maven.
- Для зависимых локальных сервисов применяй существующий Docker Compose и проверяй readiness/health, а не только факт запуска контейнера. Не сохраняй credentials в compose-файлах или заметках; используй проектные secrets/env-механизмы.
- Windows-команды и JDK-пути из заметок пользователя являются примером, а не универсальной настройкой: сначала проверь текущую ОС, установленную Java и конфигурацию проекта.
